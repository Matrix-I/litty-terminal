# v0.13.0 — Planned

Status: planned. Collects every open item carried over by earlier release
records and `ROADMAP.md` (as of v0.12.0, 2026-11-13) so they are resolved in
one release. Each item links to the record that holds its evidence. An item
is closed by a fix with its verification, or by an explicit descope with the
reason.

## Linux

- [x] **Occlusion events.** No Linux emitter for `WindowEvent::Occluded`, so
  covered or minimized windows kept rendering on PTY output (macOS fixed in
  `dc766fa`). Fixed 2026-11-13: X11 windows fold `UnmapNotify`/`MapNotify`,
  `_NET_WM_STATE_HIDDEN` and `VisibilityNotify` (`FullyObscured`) into one
  `Occluded` flag (`OcclusionTracker`); any source hides the window, all
  must clear to show it. Tests: the tracker's unit tests and
  `unmapping_the_window_reports_it_occluded_until_it_is_mapped_again`
  (real X server). Checked on real Linux 2026-11-13 (debug build, Ubuntu
  GNOME on Wayland via XWayland, a shell printing ~100 lines/s): process CPU
  over 5 s was 34–35 ticks visible, 3 minimized, 35 after restoring.
  Mutter does not unmap a minimized window, so this ran through
  `_NET_WM_STATE_HIDDEN`; a window fully covered by another was not
  checked (XWayland under a compositor reports `Unobscured`). Source:
  [perf review finding 2](../validation/2026-11-11-perf-review.md).
- [x] **Wayland window backend.** `NativeWindow::create` is X11 only; the
  Wayland surface and clipboard paths are unreachable, and IME under GNOME on
  Wayland needs a hand-started `ibus-x11` until text-input is supported.
  Descoped from v0.13.0 on 2026-11-13: a second window backend (surface,
  xdg-shell, decorations, input and keymap, text-input, clipboard) is
  weeks of work, so it gets [its own plan](./wayland-backend.md) and
  branch; X11 (XWayland under Wayland desktops) stays the Linux path.
  Source: [2026-11-11 review](../reviews/2026-11-11-linux-history-ai-graphics.md).
- [x] **Custom shaders** (GLSL to SPIR-V, offscreen targets). Done
  2026-11-13 with a new dependency, `naga` 30 (`glsl-in`, `spv-out`; MIT
  or Apache-2.0, part of wgpu), Linux only: Metal still compiles the MSL
  wrapper itself. The user's Shadertoy snippet is kept as written inside a
  GLSL 450 wrapper (uniforms as push constants, `iChannel0` the previous
  pass's render target with the linear sampler, `fragCoord` bottom-left on
  the last pass as on Metal) and compiled when the config loads; errors
  name the line in the user's file. Render targets now end their pass in
  `SHADER_READ_ONLY_OPTIMAL` and own a descriptor set; every render pass
  carries the same two subpass dependencies (earlier writes and samples
  before drawing, drawing before later samples), so pipelines stay
  compatible across passes. Pipelines are destroyed when a config reload
  replaces them. Tests (`linux_gpu/shader.rs`): compilation to SPIR-V,
  error lines, a pass that inverts a cleared render target read back on
  the GPU, and `fragCoord` orientation on the last and middle passes (both
  fail when the pass draws nothing). Checked in the real app on real Linux
  (debug build, Ubuntu GNOME on Wayland via XWayland): with an invert
  shader the window's mean RGB went from (1, 1, 1) to (254, 254, 254),
  title and prompt right side up. Not checked: a multi-pass chain in the
  app (covered by the ping-pong code shared with Metal, not by a Linux
  test) and animated shaders (`iTime`) in the app. Source: same review.
- [x] **Center new windows** on the focused monitor, as macOS does since
  `eadfda8`. Done 2026-11-13: a window opened without a position is
  centered on the RandR monitor under the pointer (X11 has no focused
  monitor; GTK and mutter use the pointer too), pinned top-left when larger
  than the monitor, and marked `USPosition` in `WM_NORMAL_HINTS` so the
  window manager keeps it. Without RandR it opens at (100, 100) as before;
  new windows from `Ctrl+Shift+N` still cascade from their source. Tests:
  `monitor.rs` centering tests and
  `a_new_window_is_centered_and_marks_its_position_as_chosen`. Checked on
  real Linux 2026-11-13 with `xwininfo`: a 1936x1240 window on a 3072x1728
  panel opened at (568, 244), the exact center. Source:
  [v0.11.1](./0.11.1.md#carried-over).
- [x] **Dead keys and Compose sent with `XSendEvent`** no longer compose since
  the keycode-0 hardening in `13073b6`; hardware keys and XTEST are
  unaffected. Descoped 2026-11-13: synthetic `XSendEvent` input is not
  supported. Xlib hands back the composed text as a keycode-0 press that
  keeps the sent flag, and such a press cannot be told from one another
  client forged, which reaches libX11's uninitialised compose-tree read
  (the crash `13073b6` fixed). Real keyboards and XTEST tools
  (`xdotool` without `--window`) are expected to compose (not checked:
  neither could be injected under GNOME on Wayland). Source:
  `ROADMAP.md` (Linux IME item).
- [x] **Legacy `WM_NAME`** stayed Latin-1 and garbled non-ASCII titles for
  window managers that ignore EWMH. Fixed 2026-11-13: `WM_NAME` goes
  through `Xutf8TextListToTextProperty` (`XStdICCTextStyle`): `STRING` for
  Latin-1 titles, `COMPOUND_TEXT` otherwise. Test:
  `titles_are_published_as_icccm_wm_name` (passes under Xvfb in a
  container). Checked on real Linux 2026-11-13 with `xprop` (release build
  of `2312ed9`, Ubuntu GNOME on Wayland via XWayland, OSC 2 title
  `Tiêu đề wmname-check ✓ 日本語`): `WM_NAME(COMPOUND_TEXT)` and
  `_NET_WM_NAME(UTF8_STRING)` both read back the full title, and
  `WM_CLASS` is `litty, litty`. Not run under a non-EWMH window manager
  (`twm` is not installed); the property itself is what such managers read.
- [x] **Vulkan failure paths** have no fault-injection tests (creation,
  submit and present results, `648f717`, `7d1e1f4`). Done 2026-11-13:
  checked Vulkan calls go through `vk_try`/`guarded`, and in tests
  `ffi::fault` can make any of them fail without running it, by name or by
  position, so the driver is left as a real failure would leave it. Tests
  fail every checked call of device setup (each gives no device), of host
  buffers (each falls back to the heap), of textures (none is left half
  built; uploads to them record nothing) and of building a swapchain (no
  frame, then the next `configure` recovers), plus a failed frame begin,
  end, submit (not presented; the fence still signals, also when the
  give-up submit fails) and present (made, then its result replaced: a
  failed present still releases its image), each followed by a working
  frame on a real window. Every test using the shared device takes
  `backend::TEST_GPU` (atlas, renderer and image tests too), since they
  share its one command buffer and upload batch; calls are logged only
  while a test watches its thread. Not covered: a failed
  `vkAcquireNextImageKHR` (skipping a real acquire is not a state a driver
  can return to) and leaks of a failed setup (it runs once per process).

## Render & Atlas

- [ ] **Bound `adjust-cell-width` / `adjust-cell-height` and `Atlas` slot math.**
  `MetricAdjust::parse` accepts arbitrary `i32`/`f32`; `cell_w > 4096`
  produces `slots_per_row = 0` and `preload_ascii` panics/aborts at
  `total_slots.div_ceil(0)` (and `cell_w * cell_h` overflows `u32` when both
  are huge). Medium severity (local `~/.litty/config` only, not PTY).
  See [verified findings plan](./2026-11-13-verified-findings-fixes.md) (Task 1).
- [ ] **Linux `rasterize_color` negative `pitch` parity & checked size.**
  FreeType keeps `bmp.buffer` at the lowest address (`y * abs(pitch)` never
  reads OOB, confirmed against `libfreetype.dylib`), so only a vertical flip
  is possible if `"Noto Color Emoji"` ever returns `pitch < 0`; align row
  reversal with `blit_ft_bitmap` and add `checked_mul` guards. Low severity.
  See [verified findings plan](./2026-11-13-verified-findings-fixes.md) (Task 2).

## Graphics

- [ ] **Linux Kitty `t=s` `/dev/shm` truncation check (`SIGBUS`).**
  macOS rejects concurrent `ftruncate` (`EINVAL`) and fails on `MAP_PRIVATE`,
  so keep `MAP_SHARED` on macOS. Check on a real Linux host whether same-UID
  `/dev/shm` truncation triggers `SIGBUS` and whether Linux can read `shm_open`
  fds via `read_range` instead of `mmap`. Low severity (same-UID only).
  See [verified findings plan](./2026-11-13-verified-findings-fixes.md) (Task 3).
- [ ] **Optional `apc_buf` `<= 64 KiB` idle retention check.** Low severity
  (cleared before next APC at `grid/mod.rs:839`; confirm pool reuse vs shrink).
  See [verified findings plan](./2026-11-13-verified-findings-fixes.md) (Task 4).

- [x] Kitty `a=d`: alternate-screen scoping of deletions against the grid
  caller. Done 2026-11-13: the grid passes the active screen; deletions
  touch only that screen's placements, and `A`/`I` free only image data no
  remaining placement shows (Kitty keeps one store per screen; refined by
  the follow-ups below). Test:
  `kitty_delete_on_alt_screen_keeps_main_screen_images`.
- [x] Follow-ups found in review (2026-11-13), all older than the scoping
  fix, done the same day: images remember the screen that transmitted them
  and `A`/`I` free only that screen's unused images; `d=I` with `p=`
  removes only that placement (as `i` does) and frees the data once
  nothing shows it; `Store::place` and `place_virtual` replace a same-id
  placement only on the same screen; leaving the alternate screen frees
  the images it transmitted that the main screen does not show.
  Image ids stay shared: placing an image transmitted on the other screen
  still works (Kitty would answer `ENOENT`), and re-transmitting an id
  moves the image to the sending screen, so a main-screen `d=I` then
  leaves it to eviction. `virtual_for` does not filter by screen. Source: `ROADMAP.md` (graphics follow-ups, 2026-11-12).
