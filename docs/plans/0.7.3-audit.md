# v0.7.3 baseline audit — 2026-11-03

## Environment and scope

- Source: v0.7.2, commit `a89baf70bba9c5695719c7152f64bd8954901de6`.
- Apple M1 Pro, arm64, macOS 27.2 (26B123).
- Rust 1.99.1 (`58cf8f9c3`, LLVM 23.1.1), Cargo release profile.
- Production `src/`, dependencies, and configuration were not changed.
- Tests inject probes into an isolated source copy. Allocation tracking uses the
  existing test allocator (System), extended to count requested bytes. Production
  macOS uses mimalloc, so these timings are baseline test-harness measurements,
  not a production-allocator comparison.
- An allocation call includes `alloc`, `alloc_zeroed`, or `realloc`. Requested
  bytes sum each call's entire requested size, including reallocation sizes;
  this is neither peak live memory nor RSS nor actual bytes copied by realloc.
- Timing samples are observations, not deterministic pass/fail thresholds.
  Allocation counts are observations; output assertions are correctness checks.

## Reproduction

From the repository root:

```sh
python3 docs/plans/0.7.3-audit.py
# Use the printed temporary directory as AUDIT_DIR.
# Run outside the sandbox for access to the Metal adapter.
cargo test --offline \
  --manifest-path "$AUDIT_DIR/Cargo.toml" --release audit_073 \
  -- --nocapture --test-threads=1
rustc -O --edition 2021 --crate-name geometry_audit \
  docs/plans/0.7.3-geometry-audit.rs -o "$TMPDIR/geometry-audit"
"$TMPDIR/geometry-audit"
cargo test --offline --release
cargo run --offline --release -- +bench-perf
cargo run --offline --release -- +bench-ram
```

The generator copies only source/build inputs, instruments five audit tests,
and prints the copy location. It never modifies production source. Keep the
copy until results are reviewed; temporary copies are not deleted automatically.
Use a separate Cargo target directory for the copy; do not point its
`CARGO_TARGET_DIR` at the production build cache. Run benchmarks serially
without other CPU/GPU-heavy work. Hardware, compiler,
fonts, shell configuration and allocator affect results. Test allocator counts
cover only the calling thread, excluding driver and worker-thread allocations.

## 1. Search snapshot

Fixture: `Grid::new(160, 24)`, feed 5,024 CRLF-terminated ASCII lines of either
20 or 160 `x` characters, confirming 5,000 retained history rows. Trailing blank
screen content is included. The code retains 5,024 physical row starts in both
cases (80,384 bytes of row capacity).

| Measurement | 20-character lines | 160-character lines |
|---|---:|---:|
| Column tuples retained | 105,484 | 808,704 |
| Column tuple capacity | 131,072 | 1,048,576 |
| Column capacity bytes | 3,145,728 (3 MiB) | 25,165,824 (24 MiB) |
| Text length | 105,484 | 808,704 |
| Text capacity bytes | 131,072 | 1,048,576 |
| Snapshot allocation/reallocation calls | 32 | 38 |
| Snapshot requested bytes | 6,633,880 | 52,509,080 |
| Median construction time (31 samples) | 3.515042 ms | 3.885541 ms |
| Min–max construction time | 3.407792–4.184958 ms | 3.681625–4.886292 ms |

Timer covers snapshot construction, excluding destruction of the returned
snapshot and excluding mutex acquisition/waiting. In `refresh_search`, this
construction runs under the grid lock. This is a proxy for the work under the
lock, not a measured contended lock duration or PTY stall distribution.

Correctness counterexample, exercised through the real parser:

1. Feed DEC mode 2027 and `❤️` into a 4×1 grid.
2. Feed the same into a 1×1 grid, then resize it to 4×1.
3. Both snapshots contain `"❤️\n"` and the same physical row starts.
4. Searching `❤️` yields `(0,0)..(0,1)` in the first and `(0,0)..(0,0)` in the second.

Thus rows+text cannot recover stored widths even with identical final grid
geometry. Preserve snapshot-owned cell metadata. No optimized implementation
was built; a >10x improvement is **not verified**.

## 2. AI allocations

All inputs are synthetic, created before allocation tracking; no network calls.

| Operation | Calls | Requested bytes | Encoded/output bytes |
|---|---:|---:|---:|
| One length pass over 100 `{role:"user",content:5000 ASCII x}` messages | 3,100 | 4,165,300 | 502,800 |
| `quote("x" × 500000)` | 7 | 3,500,007 | 500,002 |
| `quote` over 100,000 repetitions of backslash, quote, LF, CR, x | 11 | 10,500,007 | 900,002 |

The second fixture is exactly 500,000 input bytes, not 500 KiB. The original
2 MB estimate counted only four replacement passes and missed growth/formatting.
The measured history pass is one budget pass, not total compaction or an HTTP
request. The compaction prefix pass depends on boundaries and input size.

The source confirms two length-counting sites; the later prompt serialization
is required output. An encoded-length helper is feasible for the six current
JSON variants, but its correctness still requires equality tests for keys,
controls, Unicode, nested values and preserved compaction decisions.

## 3. Stem boost

Both gamma values checked across all 256 byte inputs: **512 equal outputs**.
The probe builds the lookup table before timing; a production static table
must be generated and validated separately. Timings use black-box inputs/table
access, 1,000,000 cycling pixel values, median of 11 samples per variant.

| Gamma | Current function | Lookup | Local ratio |
|---|---:|---:|---:|
| 0.78 | 5.288625 ms | 0.658000 ms | 8.04× |
| 0.55 | 5.351750 ms | 0.643291 ms | 8.32× |

These are isolated CPU operations, not full glyph rendering. Current code loads
`THICKEN` per invocation; the lookup microbenchmark uses an already-selected
table, so the comparison includes that selection difference. No frame-rate,
CoreText, CJK workload, or end-to-end fontdue speedup has been established.
The two static tables would occupy 512 bytes of element data.

## 4. Warm overlays and Arabic bounds

Real `Atlas` with Metal, system/default font resolution, 16 px, 160×40 instance
storage. Three warmup calls precede each measured builder invocation.

| Builder fixture | Calls | Requested bytes |
|---|---:|---:|
| Tab bar: `shell` and a long truncated title, 2 tabs | 5 | 1,560 |
| Search: query `needle`, current 0, total 123 | 3 | 56 |
| History: query `echo`, 9 results, each `echo ` + 200 x characters | 47 | 14,193 |

This invokes production builders and atlas code, without mocking them. It does
not count full application-frame allocations, exercise click/keyboard flows,
or prove pixel equivalence. The source reveals allocations beyond the original
checklist: search query collection and owned status labels; history badge,
counter, query, and result collections, in addition to preview strings.

Parser-fed `ب` followed by 31 U+064E marks produces a stored **64-byte** cluster.
The renderer's presentation-form substitution produces **65 bytes**. The probe
asserts both sizes. A 64-byte output scratch buffer is insufficient; derive its
bound from the source cluster limit and maximum replacement growth.

## 5. Tab geometry

An independent reviewer verified the source formulas and ran the preserved
Python arithmetic sweep: widths 1..400, tab counts 2..128, all available columns.

- Total cases: **10,084,181**.
- Tab count ≤ available columns: **9,734,423 cases, 0 containment mismatches**.
- Tab count > available columns: **164,882 containment mismatches**.
- Example: cols=1, tabs=3, col=0 selects tab 1 with span `[0,0)`.

The last condition is synthetic arithmetic evidence, not a reproduced UI bug;
rendering already suppresses spans below four columns. Establish reachable UI
conditions and intended behavior before fixing it. Geometry extraction remains
valid maintenance work. The close glyph is one column while its click target
is intentionally three columns; deduplication must preserve that distinction.

## 6. Layering

Source audit and the passing baseline layer test confirm exactly five tolerated
pairs: platform→config, platform→keymap, platform→AppEvent, render→split,
render→platform. Moving `PaneRect` and updating consumers targets **5 → 4**.
No runtime performance benefit has been measured. Platform callback/config
changes are separate scope, and Metal drawable setup still accounts for
render→platform.

## Existing baseline gates and limitations

| Command | Observed result |
|---|---|
| Generated audit, `cargo test --offline --release audit_073 -- --nocapture --test-threads=1` | 5 passed, 0 failed |
| `docs/plans/0.7.3-geometry-audit.rs` (compiled with `rustc`) | Completed; counts above |
| `cargo test --offline --release` | 351 unit + 4 integration tests passed; 8 pre-existing ignored tests |
| `cargo run --offline --release -- +bench-perf` | All built-in verdicts passed; ingestion 558,928 lines/s |
| `cargo run --offline --release -- +bench-ram` | All four RAM verdicts passed |

RAM output, two runs on the same commit and machine (footprint, MB):

| Scenario | Run 1 | Run 2 (re-verification) |
|---|---:|---:|
| 1 window / 1 tab | 76 | 79 |
| 1 window / 3 tabs | 92 | 66 |
| 2 windows / 6 tabs | 141 | 114 |
| After cleanup | 64 | 82 |
| Signed cleanup delta | −12 | +3 |

All four verdicts passed in both runs. The footprint varies by more than 25 MB
between runs (up to 27 MB in the 2/6 case), so a single run is **not** a usable
before/after baseline: compare optimized builds against a range from repeated
runs, not one number. The gate clamps a negative leak delta to zero. These are
values printed by the existing `footprint` parser, not higher-precision
independent measurements. This run
opens and closes real application windows/tabs. It does not measure the
separate no-window idle footprint or idle CPU invariant.

`main.rs::BenchPerf` **already includes** 20,000-line stress. The earlier review
claim that it needed a separate `+bench-stress` command was incorrect.

A more important limitation was found in `bench.rs::run_latency_benchmark`:
its section labelled "PTY Command Roundtrip" actually uses **`libc::pipe` and
same-process write/read**, not a pseudo-terminal, child shell or renderer. Its
reported average 0.002 ms and P99 0.044 ms therefore **do not verify PTY latency**.
The separate spawn subsection does call `Pty::spawn_in`, but measures startup,
not roundtrip. A real PTY/shell output-completion measurement remains necessary
before claiming the ≤1 ms PTY SLA. This audit documents the issue rather than
changing the benchmark outside the requested scope.

Similarly, the stress test feeds bytes to a parser/grid without rendering;
558,928 lines/s is ingestion throughput and its "frame stalls" are chunk times.
Feature regex timing excludes snapshot construction, so it cannot certify point 1.

The eight existing ignored tests cover live AI, GPU pixels, and manual
performance probes. They were not silently enabled or weakened. Linux runtime,
Linux table equality, complete UI flows/pixel comparison, optimized before/after
measurements, and actual PTY roundtrip remain unverified. None is represented
as a completed optimization. Cargo check/cross-check/clippy are implementation
gates; production Rust was unchanged in this documentation/probe audit.
