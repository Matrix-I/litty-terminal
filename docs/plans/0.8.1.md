## 1. P1 — Multi-Line Paste Preview Panics on Multibyte UTF-8 Boundary (CWE-20 / Crash)

- **Location**: `src/app/actions.rs:151-167`
- **Severity**: High (Application crash)

### Description & Root Cause
When a user pastes multi-line text into a shell without bracketed paste enabled (or before bracketed paste is turned on by an interactive application), Litty displays a modal confirmation dialog with a three-line preview of the pasted content:

```rust
let preview = text
    .lines()
    .take(3)
    .map(|l| if l.len() > 60 { format!("{}…", &l[..60]) } else { l.to_string() })
    .collect::<Vec<_>>()
    .join("\n");
```

`l.len()` returns the byte length of the line. Slicing with `&l[..60]` blindly assumes that byte offset 60 falls on a valid UTF-8 code point boundary. If any of the first three lines contains multibyte characters (e.g. Vietnamese diacritics, Asian scripts, Cyrillic, emoji, or typographic quotes) straddling byte 60, Rust panics at runtime with:
`byte index 60 is not a char boundary; it is inside '...'`
This causes Litty to terminate immediately, losing active terminal sessions and running tasks.

### Reproduction
1. Copy a multi-line string where line 1 consists of 59 ASCII characters followed by a multibyte character (e.g. `"A".repeat(59) + "ệ\nline2"`).
2. Trigger paste (`Cmd+V` / `Ctrl+Shift+V`) into a pane where bracketed paste is false.
3. Observe process crash with a slice index boundary panic.

### Proposed Fix
Truncate by character count rather than byte count, using `char_indices().nth()` to locate a safe character boundary (matching the convention in `src/render/renderer/ui/mod.rs:125`):

```rust
let preview = text
    .lines()
    .take(3)
    .map(|l| {
        if l.chars().count() > 60 {
            let cut = l.char_indices().nth(60).map_or(l.len(), |(i, _)| i);
            format!("{}…", &l[..cut])
        } else {
            l.to_string()
        }
    })
    .collect::<Vec<_>>()
    .join("\n");
```

### Acceptance & Regression Testing
- Add unit regression test in `src/app/actions.rs` (or `src/paste.rs`) feeding multi-line strings with multibyte Unicode characters crossing byte 60.
- Verify safe truncation without panic.

## 2. P2 — Control Socket Listener Mutates System Directory Permissions (CWE-732 / Security)

- **Location**: `src/platform/control_socket.rs:21-40` (`socket_path`) and `:66-71` (`listen`)
- **Severity**: Medium (System integrity; only reachable as root, see below)

### Description & Root Cause
Verified by code reading (not executed, because it needs root). Two paths resolve the socket directly inside a shared directory:
- Linux: `XDG_RUNTIME_DIR` and `HOME` both unset, so `socket_path()` resolves to `std::env::temp_dir().join(format!("litty-{}.sock", uid))`, whose parent is `/tmp`.
- macOS: `socket_path()` is always `temp_dir().join("litty.sock")`. The default `/var/folders/.../T/` is already user-private (`0700`), so this is harmless unless `TMPDIR` points at a shared directory such as `/tmp`.

In `listen()`:
```rust
let path = socket_path();
if let Some(parent) = path.parent() {
    let _ = std::fs::create_dir_all(parent);
    use std::os::unix::fs::PermissionsExt;
    let _ = std::fs::set_permissions(parent, std::fs::Permissions::from_mode(0o700));
}
```
`set_permissions(parent, 0o700)` chmods the shared directory. A non-root user gets `EPERM` (ignored by `let _`), so the damage requires running as root (Docker container, CI runner, administrative shell): the sticky bit is removed (`01777` -> `0700`) and other users and system services can no longer create temporary files.

### Proposed Fix
Never change permissions on a directory Litty did not create for itself.
- In both fallback branches that use `temp_dir()`, nest the socket in a per-user directory: `temp_dir().join(format!("litty-{uid}")).join("litty.sock")` (on macOS use the same layout so `TMPDIR=/tmp` is safe too).
- `listen()` creates that directory and applies `0o700` only to it. Before reusing an existing directory, reject it unless it is a real directory (not a symlink, checked with `symlink_metadata`) owned by the current uid, so another user cannot pre-create `/tmp/litty-<uid>`.

### Acceptance & Regression Testing
- Add unit test in `src/platform/control_socket.rs` that points the directory preparation at a `1777` temp directory and asserts its mode is unchanged while the socket's own directory is `0700`, plus a test that a pre-existing symlink or foreign-owned directory is rejected.

## 3. Descoped — AI Markdown Italic SGR Codes (false positive)

- **Location**: `src/ai/markdown.rs:31-34`, test at `:55`
- **Status**: Not a defect; no change in v0.8.1.

The initial scan flagged `*x*` emitting `\x1b[23m` (italic off) on open and `\x1b[3m` on close as inverted. It is intentional: the base style `BASE = "\x1b[3;36m"` is already italic, so emphasis renders upright inside the italic text and the closing code restores italic. The existing test asserts exactly this.

The originally proposed swap would be a regression: the open code becomes a no-op and the closing `\x1b[23m` turns italic off for the rest of the output. Revisit only if the base style stops being italic, together with a design decision on how emphasis should look.

## 4. P3 — Unescaped Token in Curl Config File during Self-Update Check (CWE-88)

- **Location**: `src/update/client.rs:160-166`
- **Severity**: Low / Hardening (Malformed configuration)

### Description & Root Cause
When `GITHUB_TOKEN` or `GH_TOKEN` is present in the environment, `fetch_release_from_api` injects it into curl's config file passed via stdin (`-K -`):
```rust
if let Ok(token) = std::env::var("GITHUB_TOKEN").or_else(|_| std::env::var("GH_TOKEN"))
    && !token.is_empty() {
        cmd.arg("-K").arg("-");
        stdin_config = Some(format!("header = \"Authorization: Bearer {token}\"\n").into_bytes());
    }
```
Unlike `src/ai/http.rs`, which sanitizes values passed to curl via an escaping `quote()` helper, `client.rs` does not escape `{token}`. If a token contains quotes or newlines, curl fails to parse the config or parses unintended arguments.

Exposure is limited: the token comes from the user's own environment, so this is hardening against a malformed value (a quote or newline can break the config or add curl directives such as `output =`), not a remote attack.

### Proposed Fix
Escape the token with the same rules as `quote()` in `src/ai/http.rs` (`\\`, `"`, `\n`, `\r`), by moving the helper to a shared place both modules use instead of duplicating it. Do not silently drop a token that fails validation.

### Acceptance & Regression Testing
- Unit test in `src/update/client.rs` that a token containing `"`, `\\`, `\n` and `\r` yields a single well-formed `header = "..."` line with nothing else injected.

## 5. P3 — Remove Redundant Map Lookups and `.unwrap()` in Input Path (cleanup only)

- **Location**: `src/app/keyboard.rs:108-140`
- **Severity**: Quality (no functional defect)

### Description & Root Cause
The `.unwrap()` calls cannot panic because the branch is guarded by `is_some_and`, and one extra hash lookup per key press is negligible, so this is readability cleanup, not a performance fix. It has no regression test; the existing keyboard tests must keep passing.

In `handle_key_event`:
```rust
if s.ai.get(&pane_id).is_some_and(|a| a.busy) {
    ...
    let ai = s.ai.get_mut(&pane_id).unwrap();
    ...
    s.ai.get_mut(&pane_id).unwrap().enqueue(&bytes);
}
```
The state map is probed with `get()`, followed by `get_mut().unwrap()` in multiple branches.

### Proposed Fix
Refactor to:
```rust
if let Some(ai) = s.ai.get_mut(&pane_id)
    && ai.busy {
        ...
    }
```
This removes the repeated lookups and the `.unwrap()` calls; behavior must stay identical.
