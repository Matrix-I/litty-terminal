## 1. P1 — Multi-Line Paste Preview Panics on Multibyte UTF-8 Boundary (CWE-20 / Crash)

- **Location**: `src/app/actions.rs:151-167`
- **Severity**: High (Application crash)

### Description & Root Cause
When a user pastes multi-line text into a shell without bracketed paste enabled (or before bracketed paste is turned on by an interactive application), Litty displays a modal confirmation dialog with a three-line preview of the pasted content:

```rust
let preview = text
    .lines()
    .take(3)
    .map(|l| if l.len() > 60 { format!("{}…", &l[..60]) } else { l.to_string() })
    .collect::<Vec<_>>()
    .join("\n");
```

`l.len()` returns the byte length of the line. Slicing with `&l[..60]` blindly assumes that byte offset 60 falls on a valid UTF-8 code point boundary. If any of the first three lines contains multibyte characters (e.g. Vietnamese diacritics, Asian scripts, Cyrillic, emoji, or typographic quotes) straddling byte 60, Rust panics at runtime with:
`byte index 60 is not a char boundary; it is inside '...'`
This causes Litty to terminate immediately, losing active terminal sessions and running tasks.

### Reproduction
1. Copy a multi-line string where line 1 consists of 59 ASCII characters followed by a multibyte character (e.g. `"A".repeat(59) + "ệ\nline2"`).
2. Trigger paste (`Cmd+V` / `Ctrl+Shift+V`) into a pane where bracketed paste is false.
3. Observe process crash with a slice index boundary panic.

### Proposed Fix
Truncate by character count rather than byte count, using `char_indices().nth()` to locate a safe character boundary (matching the convention in `src/render/renderer/ui/mod.rs:125`):

```rust
let preview = text
    .lines()
    .take(3)
    .map(|l| {
        if l.chars().count() > 60 {
            let cut = l.char_indices().nth(60).map_or(l.len(), |(i, _)| i);
            format!("{}…", &l[..cut])
        } else {
            l.to_string()
        }
    })
    .collect::<Vec<_>>()
    .join("\n");
```

### Acceptance & Regression Testing
- Add unit regression test in `src/app/actions.rs` (or `src/paste.rs`) feeding multi-line strings with multibyte Unicode characters crossing byte 60.
- Verify safe truncation without panic.

## 2. P1 — Control Socket Listener Mutates System Directory Permissions (CWE-732 / Security)

- **Location**: `src/platform/control_socket.rs:66-75`
- **Severity**: High (System integrity / Permission corruption)

### Description & Root Cause
When `XDG_RUNTIME_DIR` and `HOME` are unset, `socket_path()` resolves to:
```rust
std::env::temp_dir().join(format!("litty-{}.sock", unsafe { libc::getuid() }))
```
In this scenario, `path.parent()` is `/tmp` (or `/var/folders/.../T/` on macOS).
In `listen()`:
```rust
let path = socket_path();
if let Some(parent) = path.parent() {
    let _ = std::fs::create_dir_all(parent);
    use std::os::unix::fs::PermissionsExt;
    let _ = std::fs::set_permissions(parent, std::fs::Permissions::from_mode(0o700));
}
```
Attempting `set_permissions(parent, 0o700)` attempts to `chmod 0700 /tmp`. If Litty is executed as root (e.g. inside a Docker container, CI runner, or administrative shell), this removes the sticky bit (`01777` -> `0700`) on `/tmp`, preventing non-root processes and system services from creating temporary files.

### Proposed Fix
Ensure Litty never changes permissions on shared system temporary directories.
- In `socket_path()`, when falling back to `temp_dir()`, nest the socket inside a user-private directory:
  ```rust
  std::env::temp_dir().join(format!("litty-{}", unsafe { libc::getuid() })).join("litty.sock")
  ```
- Alternatively, check if `parent` is the system temporary folder before applying `set_permissions(0o700)`.

### Acceptance & Regression Testing
- Add unit test in `src/platform/control_socket.rs` ensuring that creating and binding the control socket never modifies the permissions of `/tmp` or `std::env::temp_dir()`.

## 3. P2 — Inverted ANSI SGR Italic Escape Codes in AI Markdown Renderer (ANSI Compliance)

- **Location**: `src/ai/markdown.rs:31-34` and `src/ai/markdown.rs:55`
- **Severity**: Medium (Visual corruption / Spec non-compliance)

### Description & Root Cause
In standard ECMA-48 / ANSI SGR:
- `\x1b[3m`: Italic On
- `\x1b[23m`: Italic Off (neither italicized nor blackletter)

In `src/ai/markdown.rs`:
```rust
} else if !code && s.starts_with('*') {
    italic = !italic;
    ("*", if italic { "\x1b[23m" } else { "\x1b[3m" })
```
`italic` is initialized to `false`. When the opening `*` is encountered, `italic` transitions to `true`, and the code emits `\x1b[23m` (turning italic OFF). On the closing `*`, `italic` transitions to `false`, emitting `\x1b[3m` (turning italic ON for the remainder of the output).
Line 55 asserts this inverted behavior in the test suite:
```rust
"\x1b[23mitalic\x1b[3m",
```

### Proposed Fix
Correct the emitted escape sequences:
```rust
("*", if italic { "\x1b[3m" } else { "\x1b[23m" })
```
Update line 55 in `src/ai/markdown.rs` to assert `"\x1b[3mitalic\x1b[23m"`.

### Acceptance & Regression Testing
- Unit test in `src/ai/markdown.rs` confirms `*italic*` emits `\x1b[3m` at the start and `\x1b[23m` at the end.
- Verify that terminal output renders emphasis correctly.

## 4. P3 — Unescaped Token in Curl Config File during Self-Update Check (CWE-88)

- **Location**: `src/update/client.rs:160-166`
- **Severity**: Low / Hardening (Malformed configuration)

### Description & Root Cause
When `GITHUB_TOKEN` or `GH_TOKEN` is present in the environment, `fetch_release_from_api` injects it into curl's config file passed via stdin (`-K -`):
```rust
if let Ok(token) = std::env::var("GITHUB_TOKEN").or_else(|_| std::env::var("GH_TOKEN"))
    && !token.is_empty() {
        cmd.arg("-K").arg("-");
        stdin_config = Some(format!("header = \"Authorization: Bearer {token}\"\n").into_bytes());
    }
```
Unlike `src/ai/http.rs`, which sanitizes values passed to curl via an escaping `quote()` helper, `client.rs` does not escape `{token}`. If a token contains quotes or newlines, curl fails to parse the config or parses unintended arguments.

### Proposed Fix
Validate that `token` contains only valid token characters (alphanumeric and safe token symbols), or properly quote and escape it before generating the config stream.

### Acceptance & Regression Testing
- Unit test in `src/update/client.rs` testing token validation/escaping with control and quote characters.

## 5. P3 — Eliminate Redundant Map Lookups and `.unwrap()` in Input Path

- **Location**: `src/app/keyboard.rs:108-140`
- **Severity**: Quality / Performance

### Description & Root Cause
In `handle_key_event`:
```rust
if s.ai.get(&pane_id).is_some_and(|a| a.busy) {
    ...
    let ai = s.ai.get_mut(&pane_id).unwrap();
    ...
    s.ai.get_mut(&pane_id).unwrap().enqueue(&bytes);
}
```
The state map is probed with `get()`, followed by `get_mut().unwrap()` in multiple branches.

### Proposed Fix
Refactor to:
```rust
if let Some(ai) = s.ai.get_mut(&pane_id)
    && ai.busy {
        ...
    }
```
This reduces hash map lookup overhead on hot keyboard input paths and eliminates `.unwrap()` calls.
